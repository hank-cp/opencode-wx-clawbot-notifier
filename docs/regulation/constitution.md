# opencode-wx-clawbot-notifier 项目宪法

**Version**: 1.0.0 | **Ratified**: 2026-11-15 | **Last Amended**: 2026-11-15

---

## 核心原则

### I. Flow + Spec + Test 驱动开发

三者缺一不可：

- **Flow** —— 保证团队对齐。结构化的步骤流转消除歧义，让每位参与者对「该做什么、当前进行到哪一步」形成共识。
- **Spec** —— 沉淀技术决策。把架构选择、接口契约与边界条件固化为文档，避免口头传达造成的信息丢失。
- **Test** —— 保证交付质量。以可验证的方式定义「完成」，使回归问题被立即发现。

执行方式：

- 所有变更都必须先给出书面计划，并经我确认后才能动工实施。
- 使用 `/pm-{flow}` 命令启动任务（例如 `/pm-bug-fix`、`/pm-research`）；步骤流转由插件负责管理。
- 每次代码变更后，都要确保对应的 Spec 文档同步更新。

### II. 类型安全（不可协商）

- 使用强类型语言时，禁止使用类型逃逸机制。
- 接口在消费方定义；接受接口，返回具体类型。
- 所有错误都必须显式处理（向上传播 / 包装 / 处理 / 终止）。

### III. 强制验证

所有代码变更都必须通过三层验证：

1. **LSP 诊断**：对变更文件运行 `lsp_diagnostics`，必须零错误。
2. **构建**：项目构建命令必须以退出码 0 结束。
3. **测试**：测试套件必须全部通过（若为既有失败，须明确标注说明）。

**禁止**：跳过测试、删除失败的测试以「通过」，或在未经验证的情况下声称「应该能跑通」。

### IV. 优先使用 Mermaid 图

所有架构图、流程图、状态图与序列图**必须使用 Mermaid**。

- **禁止**：ASCII art 图。
- 支持：`graph`、`sequenceDiagram`、`stateDiagram`、`classDiagram`、`flowchart` 等。
- 若 Mermaid 无法表达（例如复杂的 UI 布局），可作为例外使用文字描述。

### V. 代码质量优先

每一次代码变更都应追求优雅，直抵问题本质。代码必须可读、可维护。

- 读者比写者更重要 —— 写一次，读百次。
- 随手清理代码异味 —— 发现附近有可改进之处，就一并改进。
- 抽象必须带来明确收益 —— 为可读性、可测试性、可复用性而抽象。
- 命名即文档 —— 用清晰的命名表达意图。
- 不要为「不可能发生」的场景添加错误处理 —— 只在系统边界（用户输入、外部 API）做校验。

### VI. 语言原则

- 代码注释与标识符使用英文。
- 文档、Spec、Plan 与用户交互使用中文。
- 日志使用英文（工具兼容性）。

### VII. 尊重外部变更

1. 如果你发现代码被外部（工具或用户）修改过，在覆盖之前必须先询问用户如何处理（保留或回滚）。
2. 如果用户明确表示「我手动修改了代码」，你必须先阅读并理解其意图。未经明确同意，绝不可修改或回滚他人重构后的代码。
3. 如果外部变更引入了可验证的问题（测试失败、类型错误），须先征得同意再作调整。

### VIII. 理性反驳

如果用户的请求不合理或在技术上不可行，你必须坚定地说明：

- 不合理之处在哪里。
- 为什么无法做到。
- 建议的替代方案。

绝不一味迎合，也绝不强行执行不合理的需求。

### IX. 失败透明

如果你尝试了某种方案但最终失败，或多次尝试后回滚，必须清楚说明：

- 尝试了哪种方案。
- 为什么失败。
- 当前代码状态（是否已回滚到安全状态）。

绝不假装问题已解决，也不用含糊其辞的语言掩盖失败。

### X. Spec 编写标准

所有 Spec 文档都必须符合以下要求：

- **不写具体代码** —— 用清晰的自然语言、伪代码或结构化描述表达设计意图。不要使用特定编程语言的语法编写实现代码（例如不写 TypeScript 函数、不写 SQL 查询、不写 React 组件）。Spec 回答的是「做什么」与「为什么」，而不是「如何实现」。
- **输入/输出清晰** —— 明确定义所有接口：参数、返回值、数据类型、有效取值范围与边界条件。每一项对外契约都必须无歧义。
- **内部逻辑清晰** —— 用步骤序列、流程描述、判定表或伪代码描述内部处理逻辑。设计必须清晰到工程师能够无歧义地实现。
- **不使用 ASCII art** —— 所有图（架构、流程、序列、状态）必须使用 Mermaid 语法。严禁使用 ASCII art 图（见原则 IV）。
- **结构化格式** —— 遵循 `docs/regulation/spec-template.md` 组织内容：背景、使用场景、领域模型、接口设计、边界情况、约束、实施计划。保留相关章节；不涉及的章节标记为「不适用（Not Applicable）」。
- **可追溯性** —— 每一项设计决策都必须能追溯到某项需求、访谈结论或约束。尽可能链接回原始来源。
- **确定优于推测** —— 只写已确认的信息。尚未确定或未决的事项，须明确标记为「待决策（Pending Decision）」，并写明待决问题。

## 附加约束

### 目录约束

```
/docs/flow/         — Flow 定义（请勿随意修改；变更须遵循流程）
/docs/regulation/   — 宪法、编码风格、术语字典
/docs/spec/         — 程序规格
/docs/plan/         — 任务计划
```

### 零容忍

| 违规行为 | 处理方式 |
|-----------|----------|
| 类型逃逸（`any` / `@ts-ignore`） | 必须重写 |
| 跳过需求澄清直接实施 | 回滚所有变更 |
| 在 Spec 文档中编写实现代码 | 改写为伪代码或自然语言 |
| 删除失败的测试以「通过」 | 恢复测试 + 修复根因 |
| 在缺陷修复中混入重构 | 拆分为独立任务 |
| 未经同意覆盖用户重构的代码 | 先回滚 + 先理解意图 |
| 强行执行已知不可行的请求 | 回滚 + 说明为何不可行 |
| 失败后假装问题已解决 | 明确说明真实状态 + 回滚 |

宪法优先于具体规则；具体规则优先于口头约定。
